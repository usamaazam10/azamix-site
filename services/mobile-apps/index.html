{% include section-head.html no="01" label="Problems it addresses" id="problems-title" title="When an app is the right answer." lede="An app is worth building when people need to do something regularly, on the move, that a website can't do well. These are the situations we hear about most." %}

  • Customers expect to do it on their phone

    Booking, ordering, paying, tracking a delivery or managing an account. When customers do something repeatedly, an app with saved details and notifications can make it quicker for them and cheaper for you to support.

  • An existing app is holding you back

    It crashes, reviews mention the same problems, and every update is slow because the code is hard to change. Sometimes it can be repaired in stages; sometimes rebuilding the app on a sound backend costs less over time.

  • Staff work away from a desk

    Field teams, drivers, inspectors and technicians need to capture photos, signatures, locations and notes where the work happens, sometimes with a poor connection.

  • The app is only the visible part

    Accounts, data, notifications, payments and an admin panel for your team all sit behind the app. Projects that plan only the screens tend to discover the rest late and expensively.

{% include section-head.html no="03" label="Use cases" id="fit-title" title="Is a mobile app the right choice?" %}

A good fit when

  • People will use it repeatedly, not once
  • It needs the camera, location, notifications or offline access
  • Staff need to capture information away from a desk
  • Customers would benefit from saved details and a faster path to common tasks

Probably not needed when

  • Most visitors will use it once, so a fast website or web application serves them better
  • The main need is information rather than interaction
  • There's no plan or budget to maintain it after launch
{% include section-head.html no="04" label="Technical considerations" id="tech-title" title="How requirements decide the approach." lede="The choice between cross-platform, native and a web app isn't a matter of taste. It follows from a handful of questions about what the app has to do." %}
Three ways to put software on a phone, compared on the questions that usually decide it
ApproachStrong whenTrade-offs
Cross-platform (e.g. Flutter)You need iOS and Android, the interface is mostly your own design, and device features are the common ones: camera, location, notifications, storage.Brand-new platform features can need extra native code. Apps are somewhat larger than their native equivalents.
Native (Swift for iOS, Kotlin for Android)The app depends on deep platform integration, advanced background processing or the newest OS features on day one, or you already have native teams.Two codebases to build, test and maintain, which usually means higher cost for the same features.
Web app in the browserMost use is occasional, you want no install step, and device access needs are light.No app store presence. More limited device access and background behaviour, especially on iOS.

Questions we work through

  • Which platforms, and which device features, does the first version need?
  • Must it work offline? If so, how are conflicting changes resolved?
  • Who will maintain it in two years, and what skills will they have?
  • Which existing systems must it connect to?

Backend decisions that matter early

Old versions stay installed. You can't force every user to update, so the API has to keep supporting older app versions for a while. We version APIs and plan for a minimum supported app version from the start.

Keep logic on the server. Prices, permissions and business rules belong on the backend, where they can change without a store release and can't be tampered with on the device.

{% include section-head.html no="06" label="Security and ownership" id="ownership-title" title="Security, maintenance and ownership." %}

Security

Tokens are stored in the platform's secure storage, traffic is encrypted, and no secret keys are shipped inside the app, because anything in the app package can be extracted. Permissions such as location or camera are requested only when the feature needs them.

Store accounts

We recommend registering the Apple and Google developer accounts in your organisation's name, so the app listing, reviews and history belong to you regardless of who develops it.

Maintenance

Every year brings new OS versions, new devices and updated store rules. An app that isn't maintained gradually stops working well. Ongoing maintenance can be agreed separately from the build.

Ownership and handover

Ownership of the code and deliverables is set out in the project agreement. Handover includes the source code, build and release instructions, and documentation of how the app and backend fit together.
