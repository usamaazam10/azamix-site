How we work

No surprises, from first call to handover.

Process
Seven stages, scaled to the project
Principles
Seven habits behind the code

A software project goes well when everyone knows what's happening, what's been decided and what comes next. This page describes how Azamix runs projects and what you can expect at each stage, so you can judge the way we work before you talk to us.

{% include section-head.html no="01" label="Process" id="process-title" title="The stages of a project." lede="Small projects move through these stages quickly and some overlap, but none are skipped. Timelines are estimated once the scope is understood, not before." %}
  1. 01

    Discovery and requirements

    We learn how the work happens today, who will use the software, what it must connect to and what a good outcome looks like. We look at the actual spreadsheets, documents and tools involved, not only descriptions of them.

    From you: time with the people who do the work, and examples of real data.

    A written summary of requirements and open questions

  2. 02

    Scope, priorities and technical planning

    We separate what the first version must do from what can wait, identify the riskiest parts, and choose the technical approach. If something is uncertain, such as an integration or an AI feature, we say so and plan how to test it early.

    From you: decisions on priorities and trade-offs.

    An agreed scope, technical plan and estimate

  3. 03

    UX/UI design and architecture

    Where the project needs it, we design the main screens around the most frequent tasks, and define the data model and system structure. Changing a design is cheap; changing built software is not.

    From you: review and feedback, ideally from future users.

    Screens and an architecture to review

  4. 04

    Iterative implementation and feedback

    We build in short stages and share working software regularly on a staging environment or test build. Feedback shapes what comes next, and changes to scope are discussed openly rather than absorbed silently.

    From you: try each build and tell us what's wrong.

    Working software at regular intervals

  5. 05

    Testing, security checks and quality assurance

    Automated tests cover the important logic. We test manually across devices and edge cases, check permissions and input handling, review dependencies for known vulnerabilities, and check accessibility and performance.

    From you: acceptance testing against real scenarios.

    A release candidate you've approved

  6. 06

    Deployment, documentation and handover

    We deploy to production through an automated pipeline, watch the release, and hand over the source code, documentation, credentials and instructions for running the system.

    From you: accounts in your organisation's name for hosting, stores and services.

    A live system you can run without us

  7. 07

    Maintenance and future improvements

    When agreed, we keep the system secure and up to date, respond to issues, and plan further improvements based on how it's actually used.

    From you: a decision on what level of ongoing support the product needs.

    Ongoing support, if you want it

{% include section-head.html no="02" label="Engineering principles" id="principles-title" title="What the principles mean in practice." lede="Every agency claims quality. These are the specific things we do, which you're welcome to ask about and check." %}

  1. Maintainable architecture

    Clear separation between interface, business rules and data. Consistent structure and naming. Code reviewed before it's merged. The test: could another competent developer take it over?

  2. Appropriate technology

    Established, well-supported tools chosen for the problem and for who will maintain them. No experimental frameworks in production systems. We'll recommend an existing product when it beats building.

  3. Security and privacy by design

    Server-side permission checks on every request. Secrets in a secrets store, never in code. Personal data minimised and access logged. Dependencies kept patched. Security decisions are made in planning, not after launch.

  4. Testing and reliability

    Automated tests for important logic, run on every change. Repeatable deployments with a way to roll back. Errors reported to someone who will act. Backups are restored, not just taken.

  5. Performance and accessibility

    Pages and screens tested on ordinary devices and connections. Semantic markup, keyboard support, contrast and screen-reader labels from the first screen. Accessibility is part of "done".

  6. Clear communication and documentation

    Regular updates in plain language. Decisions and their reasons recorded. Risks raised when they appear. Documentation is written for the next person, not as a formality.

  7. Practical long-term ownership

    Source code, documentation and deployment instructions handed over. Accounts in your name. Widely known technology so others can support it. You should never be locked in.

{% include section-head.html no="03" label="Estimates" id="estimates-title" title="How we talk about time and cost." %}

No numbers before understanding

A price or deadline given before discovery is a guess. We'd rather spend a little time understanding the problem and give you an estimate based on an agreed scope, along with the assumptions behind it.

Uncertainty said out loud

Some parts of a project are predictable; others, such as a third-party integration or an AI feature, carry real uncertainty. We identify those parts and, where it helps, test them first so the rest of the plan rests on evidence.

Smaller first versions

A focused first release that real users can try usually teaches more than a long specification. Later stages can then be planned on what people actually need.

Scope changes are decisions

Needs change during a project, and that's normal. When they do, we explain the effect on time and cost so you can decide, rather than letting scope grow quietly.

{% include section-head.html no="04" label="Confidentiality" id="confidentiality-title" title="Why you won't find a client list here." %}

Confidential by default

Much of the software we build runs inside a business rather than in public, and some of our work is covered by confidentiality terms. We don't publish client names, screenshots or project details without explicit permission, and we'd extend the same care to your project.

If you'd like a non-disclosure agreement before sharing details, mention it in your first message. Instead of a portfolio, this site explains how we work, and our Insights show how we think about technology. If we publish demonstrations, they'll be built specifically for Azamix and labelled as demos, and any case study would appear only with the client's approval.
